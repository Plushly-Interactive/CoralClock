## Analytics & insights

- Browsing trends algorithms: audio vs active, user habits, improvement suggestions, etc. For browsing trends algorithms: if audio played on a website and other sites were browsed during the same time slots, assume the audio-playing website was not actively browsed but just an audio background/side window.
- Groups, labels, etc. (can serve as filters of tracking data) — user-defined groups, separate from the existing dashboard name groups / subdomains merging.
- **Today vs. same-weekday comparison** — compare today against the average of the last N same weekdays (Mondays vs Mondays), not a flat all-days average. Browsing is weekly-cyclical, so a same-weekday baseline is a more honest "is today unusual" signal.
- **Goal / target line on charts** — overlay a user-set total budget (e.g. "< X min/day across all sites") on the dashboard charts, with progress coloring. A global self-imposed budget that complements the per-site enforcement rules.
- **"↑ 2× usual" comparison value** — a secondary value showing how a metric (e.g. time spent) compares to the user's usual average; reveals whether today is an outlier. Most insightful on spent time, not block count. Could surface on the dashboard, the site page, or the blocked page (as a sub-value under "Spent today"). Worth revisiting once enough history exists to compute a meaningful average. Related to [Today vs. same-weekday comparison](#analytics--insights).
- **Suggest rules from analytics** — proactively surface "you might want to limit this" prompts when a site's usage crosses a heuristic (e.g. consistently high daily time, sharp week-over-week increase, or far above the user's per-site average). A suggestion would pre-fill the rules add card (reusing the existing `?target=<host>` pre-fill path) with a sensible default limit. Turns the passive analytics into actionable enforcement instead of waiting for the user to notice and act. Could surface on the dashboard or site page. Distinct from the existing [empty-state guidance](#onboarding), which is first-install only.
- **Streak (limit compliance)** — e.g. "4 / 7 days under limit this week". Motivational, pattern-oriented. Requires per-day limit-compliance history. Natural fit on the blocked or rules page, but it's a cross-cutting insight. Distinct from the per-site activity streak under [Site page stats](#site-page-stats).

Pairs with the [dashboard list search bar](#ui--visuals) (find, then select). Distinct from the existing name-group / subdomain-merge controls, which *combine* sites into one total rather than comparing them.

Let the user pick from a few preset palettes (including a colour-blind-safe option), saved as a pref and applied by swapping the `--color-chart-*` variables. Improves accessibility and personalization. Natural home is the [dedicated settings page](#settings--configuration).

## Well-being & intention

Most features currently implemented all act *at the limit boundary* — measure usage, compare it, then block when a budget is spent. The following act *before and around* that boundary, and on the user's subjective state rather than only their minutes. They reframe BiteGuard from a time-accountant into a well-being tool: the point isn't the count, it's whether the browsing is making life better or worse.

- **Pre-visit intention prompt ("pause before you open")** — when the user *opens* a chosen site (limited ones, or an opt-in watch-list), intercept with a brief interstitial: "What are you here to do? How long do you need?" The user states an intent and picks a time box, then proceeds; optionally the stated box feeds a soft nudge or the [focus session](#out-of-scope-v1--future) machinery. This acts at the *start* of a session, where mindless habit loops actually begin — every other surface today acts only once a budget is already spent. The inverse of the [reason / journaling prompt on block](#out-of-scope-v1--future), which captures intent at the wall *after* the limit is gone; this captures it at the door. Distinct from [soft "nudge" mode](#out-of-scope-v1--future) (a warning *during* usage) — this is a deliberate gate *before* usage. Implementation note: an interstitial requires intercepting navigation (a `declarativeNetRequest` redirect to an interstitial page, like `blocked.html`, that forwards on continue), reusing the enforcement redirect path.
- **Mood / well-being check-in + usage correlation** — BiteGuard measures *time* but never *how the user feels*. Add an optional, low-friction mood check-in (a 1-tap 1–5 or emoji scale, e.g. end of day or after a long session), stored per day, and correlate it against usage — "your lowest-rated days average 3.5 h on social", "mood dips on days you exceed every limit". Nothing in the backlog captures subjective state, yet that's the actual target a well-being app optimizes for; time is only a proxy. The correlation view is a natural companion to the [analytics & insights](#analytics--insights) comparisons (which correlate usage against *itself*); this correlates usage against *felt experience*. Privacy-sensitive data, so opt-in and local-only by default.
- **Daily intention & evening review ritual** — a lightweight recurring loop: each morning the user sets an intention ("keep social under 30 min today", "no news before noon"), each evening a 2-tap review scores how it went, building a self-authored log of goals vs. outcomes. An *active commitment + reflection cadence* — the habit-change core most digital-wellbeing programs are built around. Distinct from the [weekly summary digest](#notifications--awareness), which is a *passive, pushed recap* of what happened; this is the user *setting a goal first* and judging against it. Distinct from the [streak](#analytics--insights) stat, which is a *derived* compliance measure with no user-stated goal behind it. Pairs with [mood check-in](#well-being--intention) (the evening review is a natural place to also log mood) and could surface the morning prompt via [browser notifications](#notifications--awareness).
- **Screen-free / restraint crediting** — surface and celebrate *time **not** browsing* limited sites: "you stayed off your limited sites for 4 h today", "longest off-stretch this week: 6 h". Every metric today is time *spent* — a negative the user is trying to shrink; this makes the *absence* of usage a positive, visible, growing number, turning restraint into something rewarded rather than only enforced. The motivational inverse of usage charts. Distinct from the [streak (limit compliance)](#analytics--insights) stat (whole-day pass/fail) — this measures and rewards *continuous off-time within a day*, a finer-grained positive signal. Pairs with [earned / rollover budget](#out-of-scope-v1--future): an off-stretch could be what *earns* allowance.

## Settings & configuration

Settings: look for fixed, currently hardcoded values across the whole codebase that could be user-defined in settings.

- **Incognito / private-window handling policy** — an explicit decision and setting for whether private windows are tracked at all (likely excluded by default). Not currently addressed in the tracking docs.
- **Cross-device rule + settings sync** — everything lives in `chrome.storage.local` today, so it is per-machine: limits set on the laptop don't apply on the desktop, which is the biggest real-world loophole in a commitment device ("I'll just use my other computer"). Sync the small, structured data — `rules` and the pref keys — via `chrome.storage.sync` so limits and preferences follow the signed-in user across browsers. Tracking aggregates (`sitesByDay`, `subpagesByHour`, …) stay local: they're far too large for the `sync` quota (~100 KB total, ~8 KB/item) and are inherently per-device anyway. Needs a conflict/merge policy for rules edited on two devices and a user toggle (sync on/off, since not everyone wants it). Distinct from [BiteGuard export/import](#settings--configuration) (manual, one-shot, whole-dataset) — this is continuous and scoped to rules + prefs.

## Privacy & permissions

- **Narrower host permissions** — the manifest requests the `<all_urls>` host permission (`manifest.json`). Blocking is done with declarativeNetRequest (which doesn't need host access to redirect), and tracking only reads tab URLs from the `tabs`/`webNavigation` APIs — so the broad host grant may be reducible or removable entirely. A tighter permission set means a less alarming install prompt and an easier Chrome Web Store privacy review. Audit which features actually depend on `<all_urls>` before narrowing.

## Enforcement

Rules & matching:

- **Visit-count limits** — every rule's limit is a *time* budget today (`RULE_MULTIPLIERS` in `enforcement.js`). Add a "block after N visits this period" rule type that limits by visit count (already tracked) instead of time spent. A different enforcement axis from the existing scope/mode/period controls, which all size or scope a *time* budget. Pairs with the existing `period` (hour/day/week) for the window.
- **Rolling-7-day window** — `week` is a calendar week (resets at boundary), not a rolling 7-day window. Calendar semantics are intentional.
- **Schedule-aware rules** — limits that only apply during chosen windows (work hours, weekdays) or are stricter at certain times. Every rule is 24/7 today. Distinct from `period` (hour/day/week), which sizes the budget rather than scheduling when it applies.
- **Allowance / whitelist carve-outs under a blocked scope** — e.g. block `*.reddit.com` but always allow `reddit.com/r/programming`. Scopes only stack as more blocks today, never as exceptions.
- **Soft "nudge" mode (warn, don't block)** — a rule that shows a toast/badge at e.g. 80% of the limit instead of (or before) hard-blocking. Enforcement is all-or-nothing today.
- **Block-event log / history page** — `blocksByDay` exists for stats but there is no per-event timeline ("blocked old.reddit.com at 14:32"). Useful for understanding patterns.
- **Friction gate to disable a rule** — today the only protection is the hard block itself; an enabled rule can be toggled off, edited, or deleted instantly, so the willpower gap moves to the moment of disabling. Add an opt-in friction step before disabling/editing/deleting an **enabled** rule: a typed passphrase, a re-typed confirmation sentence, a math/typing challenge, or a timed cooldown ("this takes effect in 10 min"). Makes the commitment device actually sticky. The friction is self-imposed and stored locally — it's a speed bump, not real security (a determined user can clear extension storage or remove the extension; see below).
  - **What's possible at the "can't disable the extension" level** — there is **no extension-facing API** that prevents a user from disabling or removing the extension from `chrome://extensions`; an extension cannot defend itself from within. The only robust mechanism is an **admin/enterprise managed policy** set *outside* the extension: `ExtensionInstallForcelist` with installation mode `force_installed` silently installs the extension and hides the disable/remove controls. It's configured via OS Group Policy / Windows registry (`HKLM\SOFTWARE\Policies\Google\Chrome\ExtensionInstallForcelist`) or the Google Admin Console — not something BiteGuard can switch on itself; the user (or their admin) sets it once on the machine. Google documents even this as **best-effort**: some OSes let extensions be modified externally, so it can't be guaranteed. Practical takeaway: in-app friction is the realistic v1; a documented "lock it down with a managed policy" guide is the only true tamper-resistance, and it's an OS-level setup step, not a feature we ship. ([Chrome Enterprise: ExtensionInstallForcelist](https://chromeenterprise.google/policies/extension-install-forcelist/), [Tech Lockdown: enforce browser extensions](https://www.techlockdown.com/articles/how-to-enforce-browser-extensions))
- **Rule templates / presets** — one-click starter packs ("block social media", "block news", "block video") that add a curated host list at a sensible default limit, instead of adding each host by hand. Lowers the activation cost of setting up meaningful limits. Pairs with the [empty-state guidance](#onboarding).
- **Live usage-vs-limit on the rules page** — the rules page shows historical block stats and the form previews the *pattern*, but saved rules show no current proximity to their limit. The rules page is where limits are actually tuned, so a per-rule "X / Y used this period" would be more actionable there than the historical-only view. Related to the popup [Live "spent vs limit" progress bars](#popup), but on the management surface rather than the launcher.
- **Focus sessions (manual time-boxed lockdown)** — a user-started "I'm focusing now" mode: pick a duration (e.g. 25/50/90 min) or an end clock-time, and for that window BiteGuard *fully* blocks a chosen set of sites (or all sites that have any rule) regardless of their normal time budget. The inverse of the existing limit rules: instead of "block after N minutes *used*", it's "block entirely for the next N minutes". This is the Pomodoro/deep-work pattern — a fixed protected interval, optionally followed by a break — applied to site blocking. Started on demand from the popup or rules page, with a visible countdown and an (optionally friction-gated) early-stop. Distinct from [schedule-aware rules](#out-of-scope-v1--future) (automatic, recurring, calendar-driven) and from [pause tracking](#settings--configuration) (which *loosens* enforcement) — this is a manual switch that *tightens* it for a bounded interval.
- **Earned / rollover budget (allowance economy)** — make the time budget dynamic instead of a flat per-period cap: let unused minutes roll over to the next period, and/or let the user *earn* leisure minutes by staying under limits (e.g. every 30 min under budget grants 5 leisure min in a shared pool). Turns enforcement from pure restriction into positive reinforcement, which is more sustainable than an all-or-nothing wall. Requires a per-rule (or global) earned-balance store and a clear UI for the current balance. Distinct from the passive [streak](#analytics--insights) stat (which only *measures* compliance) — this makes compliance *spend down into more allowance*.
- **Sleep / wind-down protection** — a "no browsing after X" wind-down window aimed specifically at sleep hygiene: as the chosen bedtime approaches, escalate from a gentle nudge → a dimming/low-contrast overlay on pages → a hard block, then hold the block until a morning hour. Framed around the single most evidence-backed digital-wellbeing intervention (protecting sleep), with copy and defaults to match. Distinct from [schedule-aware rules](#out-of-scope-v1--future), which is the *generic* mechanism (any rule, any window, sizing an existing time budget) — this is a purpose-built, escalating, all-sites wind-down with a sleep frame, and could be *built on* schedule-aware rules once those exist. Distinct from [focus sessions](#out-of-scope-v1--future) (manual, bounded, daytime deep-work) — this is automatic, recurring, and circadian.

Blocked page:

- **Blocked today** — how many times the block triggered on this rule today. Slightly sobering, shows the pattern of coming back repeatedly.
- **Grace period / "5 more minutes" snooze** — a one-tap, rate-limited reprieve on the blocked page (e.g. one 5-min extension per day per rule). The current block is binary; a friction-with-escape-hatch model is more sustainable and reduces "disable the whole extension" rage-quits.
- **Block-time sound / visual cue** — the block is silent; the user only learns of it when the page redirects. A brief audio cue or animation on `blocked.html` arrival would make the moment land. Distinct from the `chrome.notifications` idea under [Notifications & awareness](#notifications--awareness), which is a system-level notification rather than an in-page cue.
- **Reason / journaling prompt on block** — a small "why do you want to keep going?" (or "what were you about to do?") text field on `blocked.html` that logs the user's answer with a timestamp and the blocked target. Turns the block moment into a beat of reflection and builds a personal log the user can review later. Distinct from the automatic [block-event log](#out-of-scope-v1--future) above (machine-recorded counts) — this is user-authored intent, opt-in, and only meaningful if there's a place to read the entries back.
- **Redirect to a chosen alternative instead of the block page** — on block, optionally send the tab to a *user-chosen productive destination* (a todo app, docs, a personal "what I should be doing instead" note, or another URL) rather than the terminal `blocked.html` wall. A configurable redirect target (global or per-rule) channels the impulse toward a substitute activity — the habit-substitution technique — instead of leaving the user staring at a dead end. The current blocked-page ideas (quotes, journaling, snooze) all improve *the wall itself*; this is the option to skip the wall entirely and land somewhere intentional. Natural home for the setting is the [dedicated settings page](#settings--configuration) and/or a per-rule field.

## Tracking

- **Track side panels — not possible with current APIs.** Vivaldi web panels fire `chrome.tabs.onUpdated` (with real URLs and tab IDs) but are always `active: false` and their window is not returned by `chrome.windows.getAll()`, so there is no way to distinguish a visible web panel from a regular background tab. The `chrome.sidePanel` API (Chrome 141+) only exposes open/close events for an extension's *own* panel page, not for arbitrary websites shown in any panel. No standard Chrome Extension API surfaces panel visibility or focus state for third-party content. Revisit only if Vivaldi or Chrome exposes a panel-visibility event.
- **Sleep / suspend handling** — the focused-window assumption fails hardest when the machine sleeps or suspends: a tab stays "focused" so `activeMs` keeps accruing across hours the user was away, inflating active time far more than mere keyboard idle. A flush gap (no alarm fired for far longer than the period) is a signal the machine was suspended; pause/clamp accrual across these gaps. Distinct from idle detection (keyboard inactivity while awake, already shipped) and screen-lock handling (the `locked` state, also handled by the idle path) — this is about the system not running at all.
- **Subpage opt-out toggle** — per-site "Track subpages: on/off" toggle on `site.html`. Default = on.
- **Per-site path patterns** — user-defined rules like `reddit.com` → keep `/r/<sub>` only, `youtube.com` → keep `?v=<id>` only. Could replace or complement raw path storage.
- **Purge non-human-readable paths** — regular cleanup of paths dominated by random characters / hashes / long IDs to reduce storage noise.
- **Switch to hour-only-for-today** — if `subpagesByHour` grows too large, keep `subpagesByDay` indefinitely; drop hour buckets older than X days.
